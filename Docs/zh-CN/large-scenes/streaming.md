# 资源驻留与预算

驻留系统决定“哪些资源现在应该在内存里”。它要同时满足三个约束：画面需要的数据要到位、内存占用有上限、加载过程不能阻塞帧。

## 原理

系统把两件事分开：

| 概念 | 含义 |
| --- | --- |
| 感兴趣集合 | 当前视图与逻辑认为需要的资源 |
| 真实驻留集合 | 已经加载并在内存中的资源 |

两者之间的差集就是待加载队列。拆开的好处是：重复请求可以合并，加载顺序可以按优先级调整，也能在预算不足时推迟加载而不破坏正确性。

## 请求与去重

- 同一资源的多次请求合并为一条；
- 请求带优先级，场景网格工件优先级高于材质与纹理解码；
- 加载提交与淘汰都在统一队列中记账，可观测请求数、提交数与淘汰数。

## 预算

预算约束三类资源：

- CPU 内存占用；
- GPU 内存占用；
- 每帧上传量。

超过预算时按优先级与使用时间淘汰，而不是直接失败。淘汰需要尊重帧回收钉子：被当前帧引用的资源不能被回收。

## 帧回收钉子

渲染是多线程的，资源在 CPU 侧不再被引用并不代表 GPU 已经用完。驻留系统保留帧回收钉子，与帧资源环和 GPU 围栏配合，确保回收发生在真正的安全点。

## 与资源队列的关系

编辑器启动使用异步场景资源管线，Windows 默认取 `pipelined`，其它平台默认取 `async`：

- 场景网格工件以高优先级提交；
- 材质与纹理解码保持正常优先级，保证队列公平性，不会因为几何体过多而把纹理饿死。

需要对照实验时可以切换回同步预热路径：

```powershell
Editor.exe --editor-startup-resource-pipeline legacy <project>
```

## 可观测性

驻留系统对外暴露请求、提交与淘汰的计数与原因。判读这些计数的方法与其它遥测一致，见[性能分析与图形调试](../quality/profiling.md)。

编辑器目前把遥测汇总开关用于缩略图侧（`--editor-thumbnail-telemetry-summary <path>`）；驻留计数随渲染器统计一起发布，没有独立的汇总开关。

## 当前边界

- 地形与世界分区尚未实现，因此“按区域流式加载世界”还没有落地；
- 立方体贴图运行时加载与流式 Mip 仍是扩展点，见[模型、网格与纹理](../assets/models-textures.md)；
- 预算默认值偏保守，需要按项目实测调整。

这些边界记录在[功能状态矩阵](../roadmap/index.md)，实现顺序取决于对应章节列出的依赖。
