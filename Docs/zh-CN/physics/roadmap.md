# 物理现状与规划

本页说明物理与交互能力的当前状态、缺口与依赖。

## 当前状态：规划中

### 已有

- 项目文件中有 `gravity` 键，作为全局重力加速度的配置项；
- 组件更新循环包含固定步长阶段 `OnFixedUpdate`，脚本可以按固定步长执行逻辑；
- `Time` 提供 `fixedDeltaTime`（默认 `0.02`）与 `maximumDeltaTime`（默认 `0.1`），并暴露 `fixedFrameCount` 用于确定性逻辑。

### 缺失

- 没有刚体、碰撞体、触发器、射线或形状查询；
- 没有碰撞检测与求解，没有摩擦与恢复系数；
- 没有角色控制器；
- 没有物理调试可视化与物理材质。

`gravity` 目前是配置项而不是被物理解算消费的输入。

## 目标

| 能力 | 目标描述 |
| --- | --- |
| 碰撞形状 | 盒、球、胶囊、凸包与三角网格 |
| 刚体 | 质量、阻尼、运动学与动力学模式 |
| 碰撞检测与求解 | 接触生成、约束求解、摩擦与恢复 |
| 查询 | 射线、扫描与重叠查询 |
| 触发器 | 无响应碰撞的进入、停留、离开事件 |
| 场景查询接口 | 与场景对象层级和空间索引协作 |
| 角色控制器 | 胶囊驱动、地面检测、台阶与斜坡 |
| 调试可视化 | 在编辑器视口显示碰撞体与接触 |

## 依赖与顺序

1. 物理需要一个**第三方求解器**或有明确边界的自研内核。选择求解器属于架构决策，不能由实现者临时决定。
2. 固定步长更新已经存在，物理步进可以接入该阶段；需要补充的是子步与插值策略。
3. 物理对象需要与空间索引协作，避免物理查询退化为全场景扫描，见[可见性与遮挡剔除](../large-scenes/visibility-occlusion.md)。
4. 物理组件是新的反射类型，需要按[反射与序列化](../architecture/reflection-serialization.md)接入序列化与 Inspector。
5. 物理 API 进入脚本清单后，C# 与 Lua 两种绑定由同一份清单生成，见[脚本 API 参考](../scripting/api.md)。
6. 角色控制器可以先做运动学版本，不阻塞在完整求解器上；但它与物理系统共用形状与查询基础设施，重复实现会带来两套语义。

## 与动画的关系

动力学角色控制依赖物理求解器；运动学角色控制首先依赖形状、扫掠与碰撞查询。动画状态机用于表现联动，不是运动学控制器的前置条件。两条实现路径可以交错，见[动画现状与规划](../animation/roadmap.md)。

## 不作为承诺

本页描述的是目标与依赖，不是排期。实现状态变化时以[功能状态矩阵](../roadmap/index.md)与源码为准。
